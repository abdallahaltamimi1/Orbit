# ORBIT database analysis and SQL Server proposal

Revised design review draft — 5 November 2026. Analysis only; no backend, database connection, SQL execution, package installation, or runtime change is included.

## Coverage and scope classification

This proposal covers the **school academic, channel/assignment, recruitment, event/meeting, moderation and notification slice**, together with its backend support. It is **not complete ORBIT database coverage**. “Current required” includes user-approved corrections to prototype behavior; it does not mean every guarantee already exists in JavaScript. The audit remains source evidence; the catalog describes the revised target.

| Scope | Tables in this catalog | Boundary |
|---|---:|---|
| Current required functionality | 69 | All catalog tables except the 11 supporting tables listed below. Includes stable people/rosters, annual academics, promotion/graduation review only, primary teaching assignments, timetable history, channels/content/submissions/evaluation, recruitment, captured meeting audiences, moderation and notifications. Typed domain histories remain here because their preservation is required. |
| Supporting backend infrastructure | 11 | AspNetUsers, AspNetRoles, AspNetUserRoles, AspNetUserClaims, AspNetRoleClaims, AspNetUserLogins, AspNetUserTokens (7 Identity tables), Files, AuditEvents, OperationReceipts and OutboxMessages. **Excluded existing features:** subscription plans, trials/expiry, entitlements, personal-vs-school subscription selection and quota/usage accounting (`shared/subscriptions.js`, `shared/subscription-config.js`); lesson-planner/studio project documents (`lesson-planner/studio-service.js`); generated lessons/questions, practice/quiz attempts and personal learning progress (`shared/student-learn.js`, `shared/learning-service.js`); achievements and personal saved/liked content (`achievements/achievements.js`); personal themes/language/mood and other UI state. School memberships/permissions stored inside the subscription service are included, but its subscription/entitlement domain is not. **Deferred additions:** unspecified graduation confirmation/revocation and resulting graduated roster state; RSVP and attendance; supporting/co-teacher assignments; private-channel approval requests (currently reserved only); unspecified report intake beyond existing report review. Terminal-grade graduation review and captured meeting recipients stay in scope. No GradeProgressions configuration table or StudentGraduations table is retained. Safety/history/delivery infrastructure is not deferred to reduce table count.

### Verified ORBIT rules and conflicts

| Requested rule | Audit result / proposal |
|---|---|
| Upcoming/Active/Archived; at most one Active | Present. DB filtered unique index enforces the maximum; activation transaction archives old Active and activates Upcoming. Zero Active is valid before first activation. |
| Student provisioning includes enrollment | Main workflow complies. Legacy issuance-only API is a gap; production school-student provisioning must be atomic and include initial placement. |
| First-login password change; no plaintext storage | Main provisioning stores salted digests and a flag; one-time UI receipt is memory-only. Future Identity hash replaces custom browser digest. Never persist temporary plaintext in tables, audit, outbox or logs. |
| Existing-account ownership verification and approval | Teacher invitation consent is implemented, but browser login is not trustworthy proof. Student confirm/correct mapping allows school-only confirmation without account-owner approval: conflict. Use a verified, expiring linking workflow for both. Subscription addMember also bypasses this academic linking workflow. |
| Sunday–Thursday, seven periods, no lesson times | New service complies. Legacy timed/weekend services conflict and coexist; quarantine/manual mapping, not automatic conversion. Learning meetings/interviews/events still legitimately have times. |
| Published timetable remains available | New drafts retain publishedVersionId and memberRead uses it even while status is draft. Teacher memberRead can include historical years; studentEnrollment requires Active, and the main memberTimetables projection filters Active for both. Historical member visibility is inconsistent with a broad reading of “remain available”; proposed policy is read-only historical access through historical verified enrollment/assignment. Needs review. |
| Promotion preview/confirmation/history; no automatic graduation | Graduation execution remains deferred. Approved target: standard numeric grades 1–12 derive progression automatically; grade 12 opens GraduationReview, with no automatic graduation or required administrator progression configuration. |
| Opportunity states; FullTime/PartTime | States comply. Existing UI also offers contract and uses full-time/part-time; putJob only requires nonempty employment text. Conflict: proposed DB permits only FullTime/PartTime; Contract needs explicit migration disposition. |
| Applications only for Published | Present in apply. DB FK alone cannot enforce parent status; transaction locks/rechecks it. Closing must not erase existing applications. |
| Sequential interviews/manual completion before next/final | Source conflict: current final-decision guard only rejects Scheduled interviews and permits decisions without a completed interview. | Rescheduling reason/proposed time; confirmed appointment unchanged until approval | Present. Pending request does not modify appointment. Approval rechecks original slot/revision, duration, ownership and overlap. Preserve original, proposed, decided and resulting slots. |

## 2. Modeling conventions (apply to every catalog row)

This is a logical/physical design specification, not executable DDL. All catalog tables below are proposed for this slice. Guid-based Identity and domain keys remain a proposed architecture decision, not a conversion of existing application IDs; no IDs or migrations are changed here. Additions without a present workflow are explicitly marked **new**. ASP.NET Core Identity is the authentication boundary; school membership and resource-scoped policies are additional authorization, not Identity roles alone.

- `G` = `uniqueidentifier`; `T` = `datetime2(3)` UTC; `D` = `date`; `S` = `SchoolId G NOT NULL`; `Y` = `AcademicYearId G NOT NULL`. A column is **NOT NULL unless suffixed `?`**. `?` means NULL with no default. No default exists unless written `=...`.
- In catalog columns, `Id G` is the PK and defaults to `NEWSEQUENTIALID()` unless a composite PK or shared PK is explicitly stated. Identity's Guid user/role IDs are generated by its configured application stores instead. Small lookup codes use their stated PK and no generated default. `int identity` is explicitly identified.
- `C` expands to `CreatedAt T = SYSUTCDATETIME()`. `M` expands to `C, UpdatedAt T = SYSUTCDATETIME(), Version rowversion`. UpdatedAt is updated explicitly by the application; its default is insertion-only. `rowversion` is an opaque concurrency token, not a date or audit version. Every use of these abbreviations is a complete column declaration.
- `ActorId`, `CreatedById`, `DecidedById`, `RequestedById`, `VerifiedById`, `CompletedById`, `RecipientId`, `OwnerUserId`, `UserId` and other expressly named user IDs are `G` FKs to `AspNetUsers.Id` wherever present. A `?` actor allows imported/system actions; system events must carry provenance. These references never use email.
- All FKs have `ON DELETE NO ACTION`, `ON UPDATE NO ACTION`, including Identity relationships (explicitly override cascade conventions). No catalog omission means cascade. Use archive/removal status and retain users as disabled tombstones. Physical deletion is a separately reviewed retention process, not part of this design.
- `U(...)` denotes an unfiltered UNIQUE constraint; `UX(...) WHERE ...` a unique filtered index; `IX(...)` an ordinary index. Every FK gets an index with its columns as the leftmost prefix unless a listed PK/U/IX already covers it. Child FK = parent PK unless a tuple is specified. Unfiltered alternate keys are used as FK targets; filtered indexes are not FK targets.
- Every table with S has FK `SchoolId -> Schools.Id`; every table with S,Y has FK `(SchoolId,AcademicYearId) -> AcademicYears(SchoolId,Id)`. Every Id table with S also has `U(SchoolId,Id)`; every Id table with S,Y additionally has `U(SchoolId,AcademicYearId,Id)`. These are explicit candidate keys for scoped FKs, not independent entities. Composite child tables inherit the same school/year FKs when S/Y are declared.
- Within school tables, a school-parent ID always uses `(S,ParentId) -> Parent(S,Id)`; for year parents use `(S,Y,ParentId) -> Parent(S,Y,Id)`. The catalog spells out additional wider tuples wherever two sibling references must agree. This redundancy is deliberate integrity protection. Do not configure separate unscoped FKs as a replacement.
- Required names/reasons/text must pass `CHECK LEN(LTRIM(RTRIM(column))) > 0`; optional text is NULL rather than blank. Text is Unicode `nvarchar(n)`. All status/type fields are `varchar(n)` with CHECK membership in the exact set listed below, using case-sensitive comparison/collation for canonical codes. IDs never encode status, school, email or year.
- `NormalizedName`/`NormalizedCode` are bounded Unicode columns filled with one shared NFKC/trim/case-fold normalization routine. DB uniqueness guarantees uniqueness of stored canonical values; Unicode canonicalization itself is an application rule. Use explicit agreed collation (including Arabic behavior), validate normalization before writes, and audit aliases during import.
- JSON, where explicitly used for immutable audit/disclosure snapshots, is `nvarchar(max)` with `CHECK (ISJSON(column)=1)` when non-NULL. It is not used for operational relationships, permissions or arrays of FK IDs. List facets have child tables.
- All constraints named in a table are in addition to the conventions. No other hidden business columns are implied. Relationships below are 1:N parent-to-child unless U/shared PK makes them 1:0..1; junctions implement N:M. Nullable FK means an optional parent. The database does not enforce a parent's minimum number of children; aggregate completeness is transactional.

SQL Server/Identity references checked for this proposal: [Identity model customization](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/customize-identity-model?view=aspnetcore-10.0), [SQL Server PK/FK constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/primary-and-foreign-key-constraints), and [filtered indexes](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/create-filtered-indexes). Framework-generated Identity schema must be checked against the chosen package/schema version before producing DDL; this proposal fixes Guid keys rather than relying on default string-key scaffolding.

## 4. Relationship map and aggregate boundaries

- Users N:M global roles via AspNetUserRoles; users 1:0..1 UserProfiles, Students and Teachers independently. Schools N:M user accounts through SchoolMemberships, with role-specific permission children. An organization can have multiple managers (**proposed**, replacing school-email ownership); retain at least one active manager transactionally.
- Students 1:N SchoolStudents over schools; Teachers 1:N SchoolTeachers over schools. Each school roster identity persists across years. Approved linking assigns the canonical person.UserId and writes history; it does not create an annual person copy. School membership references the same user, checked on linking/provisioning.
- School 1:N years, grades, subjects and roster records. Grade 1:N Sections; Year 1:N Sections. SchoolStudents 1:N annual enrollments; annual enrollment 1:N placements; Section 1:N placements. A current enrollment requires exactly one open placement. GraduationReview is a retained promotion decision; actual graduation is deferred with no aggregate/table in this catalog.
- PromotionBatch has two distinct year roles (source/target) and N decisions. Each decision references one source enrollment and at most one resulting target enrollment for the same school student. No year's activation is implicitly part of promotion.
- SchoolTeachers 1:N TeachingAssignments, each for one year/section/subject. Replacements retain referenced prior rows. Section 1:0..1 Timetable for its year, timetable 1:N revisions, revision 0:N cells. Each current published cell has one occupancy row; no rows for empty slots. Teacher change request points to its original published cell and optional resulting revision.
- Channel 1:N Posts and LearningMeetings; School channel N:M Sections via ChannelSections. Post N:M targeted sections is a subset of channel targets. Independent channel N:M accounts via explicit membership; school-channel admission is derived from enrollment. Ownership history does not rewrite Authors/Evaluators.
- Post 1:0..1 Assignment. Assignment 1:N Submissions, one/student; Submission 1:N immutable versions; version 0:N files and evaluations. School submission version references a placement and authorized post section for the same school/year. Files N:M posts/submission versions/applications through typed junctions.
- Opportunity 1:N Applications; Teacher 1:N Applications. Application 0:N sequential Interviews; Interview 0:N reschedule requests and history events. Status-history interview references are constrained to their own application. Files disclosed at application time remain linked after profile changes.
- SchoolEvent N:M yearly Sections when targeted; LearningMeeting optionally references a reusable channel group and N:M recipient accounts; group member changes do not rewrite captured recipients. Notifications belong to one recipient and optionally one typed resource. Audit/outbox entries supplement domain histories; they do not replace domain FKs.

All relationships use restrictive deletes. Removal means disabled account, removed membership, retired assignment, archived year/channel, hidden/deleted post, withdrawn application or cancelled appointment as appropriate. No School -> Users, Year -> Enrollment, Channel -> Submission or Application -> Interview cascade is safe here. Child physical cleanup must run explicitly in dependency order after approved retention rules; Identity cascades also remain disabled.

## 5. Database guarantees versus application/transaction rules

### Proposed database-enforced rules

1. PKs, typed FKs, scoped alternate keys and sibling composite FKs prevent cross-school/year section, placement, assignment, cell, post target, promotion enrollment and recruitment ownership mismatches. Nullable composite FK tuples have explicit all-or-none CHECKs where optionality is allowed; SQL Server otherwise bypasses an FK containing NULL.
2. Uniqueness: canonical email/usernames, school/year names, one Active year/school, section name per grade/year, school roster codes/person, annual enrollment/student/year, one open placement/enrollment, one active primary assignment/section/subject/year, one table/section/year, one occupied cell/revision/slot, one current published teacher/section/slot, one application/teacher/opportunity, one scheduled interview/application and one pending reschedule/interview.
3. Enumerated statuses/types, positive revision/sequence numbers, sensible date order, fixed timetable days/periods, grade range, correct XOR target columns, duration bounds, decision timestamp coherence and JSON validity. Name/reason length/nonempty rules use SQL type bounds and CHECKs.
4. Restrictive deletion and stable identifiers preserve references. Rowversion supports concurrency detection but does not itself make multi-row writes atomic. Unique keys are still needed even if the UI prechecks duplicates.

### Application rules executed transactionally

All write paths use authenticated identity, policy authorization scoped to the resource's SchoolId, first-login restrictions, optimistic rowversion checks, and an explicit SQL transaction for aggregates. EF query filters are helpful but are not an authorization or integrity guarantee. Catch duplicate/concurrency errors and return a reload/review result, not silent overwrites.

## 7. Assumptions, proposed additions and unresolved decisions

### Remaining material decisions (recommendations are not approval)

1. **Teacher affiliation:** recommended default is one active school per teacher, retaining the current membership rule/index. Consequence: PartTime does not itself permit multiple active school memberships. Multiple schools require removing that index and resolving cross-school numbered-calendar/conflict rules; multiple recruitment applications remain allowed either way.
2. **Historical timetable access/corrected identity:** recommended default is read-only historical schedules for verified former members, but no retained access for an account wrongly linked and later corrected. Consequence: authorization must use reviewed person/enrollment/assignment history, not an old email or current membership alone. Current student code is Active-only; this recommendation still needs approval.
3. **Legacy Contract opportunities:** recommended default is quarantine Contract/unknown values for explicit per-record FullTime/PartTime classification before import. Consequence: those records cannot enter the production catalog until resolved; preserve raw history and do not guess or extend the approved enum. No conversion occurs now.
4. **Retention/anonymization:** recommended design default is restrictive deletes and retained references, not indefinite production retention approval. Set retention/access/anonymization periods for student work, application disclosures/files, interviews and audit before production. Consequence: no automatic purge or destructive cascade is designed now.

Progression, manual teacher-code entry, primary-only assignments, completed-interview gating, cancellation replacements and graduation execution/RSVP/attendance deferral are resolved by the revision instructions, not open questions. Guid IDs remain explicitly proposed architecture; do not convert existing IDs. Existing deferred domains need separate scope before claiming complete ORBIT coverage.
### Explicit design assumptions / additions

- Guid Identity keys, one normalized email/account, multiple scoped school managers and optional multi-role users are proposed architecture choices. Managers own schools through membership, not matching school account email. Additional organization staff/delegated roles require future policy, not an unbounded permissions framework now.
- Stronger owner-verified student linking, link expiry, immutable review versions, outbox/idempotency and server upload metadata are new server requirements. Existing UI consent is retained as workflow evidence, not proof of real-world identity or credentials.
- Cross-school student overlapping-year enrollment remains prohibited per the current check, enforced transactionally against canonical StudentId. School year overlap is prohibited for non-archived years, as current code does. This is not a universal calendar/year label constraint.
- SchoolStudents and SchoolTeachers are institutional roster records, not duplicate login accounts. Global Students/Teachers are stable person-role identities. Institutional name snapshots, timetable labels and application disclosure snapshots intentionally retain history; operational relationships remain normalized.
- School events can be yearless; section-targeted events cannot. Learning meetings are separate from recruitment interviews even though the prototype stores them together. Meeting attendance/RSVP and unspecified report intake are deferred; captured recipients and existing report review remain in scope.
- No guardian, attendance register, report card, fee collection, payroll, hiring contract, subject examination/final mark, chat messaging or enrollment-based subscription entitlement is inferred. Assignment evaluation is not a final course grade.
- Subscription plans/usage/billing, lesson planner documents, generated learning quizzes/progress, achievements, saved likes and personal UI preferences exist outside the requested school/recruitment database slice (`shared/subscriptions.js`, `lesson-planner/studio-service.js`, `shared/student-learn.js`, `shared/learning-service.js`). They are **deferred**, not silently mapped to arbitrary key tables. If the next phase must persist these end-to-end, separately audit and extend their domain schemas before claiming whole-platform backend coverage. Existing subscription gates must remain application inputs until that scope is approved; no payment data is modeled here.

No SQL or EF model was generated, compiled or connected to SQL Server. These are reviewed design declarations, not validated DDL. Provider/version syntax, collation, actual index widths, nullable uniqueness, dependency ordering and concurrency behavior still need executable verification in a later authorized phase.
- **Missing relationships:** added explicit post-target subset, placement-at-submission, source/destination promotion identity, interview-to-application teacher, reschedule-to-interview and membership-to-school links. Indirect scope is documented where the parent uniquely determines it. Required child existence is reserved for transactions.
- **Type consistency:** all user/domain/scoped IDs are G, no email foreign keys; UTC instants T and date-only due/year fields D; timezone stored where civil date/time matters. Grades use decimal(5,2); copied rowversion tokens binary(8). Status capitalization is canonical and legacy mappings are explicit.
- **Duplicate entities:** one Sections entity replaces classes+sections, one account system replaces browser accounts, one canonical person mapping replaces reporting/enrollment/teaching identity projections. Assignments are a post subtype; evaluations attach to submitted versions; derived monitoring/membership/late states do not get redundant status tables. Domain events do not replace business entities.
- **Deletion/history:** all FKs NO ACTION; no cascade chains through historical academic/recruitment data, Identity, files or audit. Current occupancy is a replaceable projection, revisions are retained. Assignment retirement and interview/request cancellation preserve prior facts; unspecified graduation revocation is deferred. History immutability requires controlled write permissions/commands.
- **Scope mismatches:** composite FK tuples prevent school/year mixing, including school-channel multi-section posts, yearly publication cells and promotion enrollment identity. Remaining cross-parent/date/authorization checks are expressly transactional, not implied by simple FK presence. NULL composite keys have all-or-none checks where needed.
- **Static SQL Server design review (not execution validation):** filtered uniqueness handles maximum Active/pending/open rows; FK targets are unfiltered PK/U keys; FK indexes are explicitly required. Wide tuples remain below normal SQL Server key width limits (mostly Guid keys and small numbers); long JSON/URL/body fields are never key columns. Circular table references need ordered FK creation; nothing relies on deferred constraints.
- **Concurrency:** duplicate checks alone are insufficient. Publication projection unique keys, application scheduling locks, person-based enrollment locks, rowversion and idempotency protect races; no trigger-dependent guarantees are implied. Histories get per-parent sequence under lock, not application-wide unprotected MAX+1.
- **Limitations:** schema has not been compiled into DDL or tested against SQL Server because that is explicitly the next phase. Final EF/Identity package model, exact CHECK syntax/index names and migration ordering must be verified when generating approved scripts; no executable schema or backend was created here.
